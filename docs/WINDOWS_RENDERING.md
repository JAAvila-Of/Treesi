# Windows rendering fallback

On Windows, open **Settings** in the repository tab bar to choose **Automatic (recommended)** or **Software compatibility**. Automatic remains the default. Software compatibility can help virtual or problematic graphics devices with high CPU use or display issues. Save the preference, then close and reopen Treesi when convenient; saving never restarts the app or discards open repository state. Return to Automatic through the same dialog and reopen the app to undo the choice. The dialog supports both themes, keyboard navigation, cancellation and save-error feedback.

The per-user `Treesi/graphics.json` preference is read before initializing the windowing subsystem. Reads are limited to 4 KiB; absent, malformed or unknown values select Automatic. Writes replace the file atomically. A failed save keeps the previous preference and does not pretend that the next startup has changed. Software mode skips the hardware probe entirely. The setting applies only to Windows; other platforms keep their existing rendering selection.

In Automatic mode, Treesi keeps Avalonia's default rendering selection when a non-software DXGI adapter can create an explicit Direct3D 11 device, or when adapter detection is unavailable. If enumeration succeeds but no usable hardware device is found, it selects Avalonia's direct software renderer instead of sending GPU work through a CPU-emulated Direct3D device. The device probe supplies the specific adapter with driver type `UNKNOWN`; it never requests a WARP driver. Temporary device and context interfaces are released.

This is a product startup policy, independent of tests, repository content and environment flags. It does not disable the caret, change motion preferences or alter themes. Linux and macOS keep their platform defaults. Adapter detection is bounded to 32 entries and uses the documented `DXGI_ADAPTER_FLAG_SOFTWARE` bit plus device-creation capability, not adapter-name heuristics. Failed enumeration preserves Avalonia's normal compatibility path. The descriptor ABI is checked without calling native APIs in the headless suite.

Native stacks in the isolated Windows VM identified `d3d10warp.dll!PixelJITProcessor::ExecuteJIT` and triangle-rasterization work on the five worker threads responsible for most focused-input CPU. [WARP](https://learn.microsoft.com/en-us/windows/win32/direct3darticles/directx-warp) is Microsoft's software Direct3D rasterizer. This motivates comparing direct CPU rendering for hosts with no hardware adapter. A shared VM does not establish performance or visual acceptance on physical GPUs; native UI tests and process measurements remain necessary.

References: [DXGI adapter flags](https://learn.microsoft.com/en-us/windows/win32/api/dxgi/ne-dxgi-dxgi_adapter_flag), [adapter enumeration](https://learn.microsoft.com/en-us/windows/win32/api/dxgi/nf-dxgi-idxgifactory1-enumadapters1), [descriptor layout](https://learn.microsoft.com/en-us/windows/win32/api/dxgi/ns-dxgi-dxgi_adapter_desc1), [device creation](https://learn.microsoft.com/en-us/windows/win32/api/d3d11/nf-d3d11-d3d11createdevice).

The isolated performance workflow accepts an explicit saved graphics preference, defaulting to Automatic. It prepares the normal preference file only inside its disposable VM and launches the production executable. Reports identify the requested preference; a successful test protocol does not itself mean that provisional CPU targets passed. The separate rendering-lab experiment remains distinct from these production-entrypoint measurements.
