# Isolated Windows rendering comparison

The manually dispatched `native-rendering.yml` workflow compares explicit ANGLE and direct software rendering on one disposable interactive GitHub-hosted Windows VM. It never runs native UI on developer machines, self-hosted runners or the SSH benchmark host.

`Treesi.RenderingLab` is a separate guarded launcher referencing the product's `App`; the production entry point and rendering policy remain unchanged. It selects one rendering mode with no fallback to the other. The native test requires the initialized graphics service to match the requested mode: D3D11 ANGLE for `angle`, no platform graphics service for `software`. Read-only reflection into Avalonia's version-pinned implementation services is confined to this diagnostic tool. The recorded service identity is not a GPU usage measurement, driver identity or presentation timestamp.

The launcher uses the SDK-installed runtime in the VM through a framework-dependent publish; restores remain locked without adding a runtime identifier to the shared product lock files. Both rendering routes use the same launcher and runtime. Its console is hidden without hiding the application window.

The protocol uses a single synthetic repository with 1,000 background files and 10,000 imported commits. Each fresh process loads a 1,000-commit graph. Samples run in ANGLE, software, software, ANGLE order. Each records 60 seconds with search focus and 20 seconds with graph focus, after three seconds of settling. Focus and matching DPI are checked. Resource windows contain no UI automation queries, profiling or forced garbage collection. The caret, motion settings and application controls are unchanged. Both theme screenshots precede measurement, which always uses dark theme.

Artifacts include initialized-service diagnostics with process identity, resource samples, per-thread endpoint observations, screenshots and a completion report. Partial protocols remain incomplete. These are experiments using an explicit lab startup, separate from the production startup baseline. Alternating order reduces a simple order bias but does not remove shared-host variation or establish acceptance on physical GPUs. Presentation timing, long-session retention and actual GPU behavior require separate evidence.
